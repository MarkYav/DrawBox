# DrawBox v2 Design Doc (GREEN)

## Objective

The objective of this doc is to propose a new architecture for DrawBox v2.

## Background

This library is based on Compose Multiplatform that enables it to be used across multiple platforms.
A user can draw on a `Canvas` by touching or dragging his finger on the screen.
Then, the `Canvas` is converted to an image.

The idea of creating this open-source project appeared because I needed a multiplatform (Android + desktop) library for drawing.
I found several popular libs for Android but there was **ZERO** for using in KMP (Kotlin Multiplatform).
Right now, there are several libraries already, so the goal is to extend the functionality to make the library cover more use-cases.

DrawBox targets **application developers building on KMP who need a drawing canvas that works out of the box.**
It optimizes for approachability and a small, comprehensible API surface.
The working assumption is that large teams and organizations with bespoke requirements will build their own tailored implementation regardless.
Therefore, DrawBox aims to cover the common ~80% cleanly rather than to be maximally configurable.
Where extension is offered, it is offered as the *simplest mechanism that meets the need*, not a general plugin framework.

## Requirements

### 2.1 Goals

- **All KMP targets.** Android, Desktop (JVM), iOS, and Web (Wasm/JS) must all work from the single common codebase.
- **Any aspect ratio** — drop the square-only constraint.
- **Resolution independence** — geometry is stored independent of pixel size; window resize is lossless; export is sharp at any requested resolution.
- **Lossless, uniform undo/redo** that is uniform across every kind of edit.
- **A hybrid vector + raster model** — an immutable vector command log is the source of truth, rendered into a raster buffer that backs display and pixel-level tools.
- **Core tool set:** brush, shapes (line / rectangle / ellipse), flood fill, two erasers (pixel-erase and action-erase), eyedropper, text.
- **Data-level extensibility** — new brushes can be added without forking and without subclassing tools.
- **Two-line "hello canvas"** — everything beyond `DrawController()` + `DrawBox(controller)` is opt-in via defaults.
- **Modularity** — minimal-dependency core, with optional UI and serialization modules.

### 2.2 Non-Goals (for 2.0)

- **Zoom & pan** (normalized coordinates make this a non-breaking later addition).
- **Layers** (an optional `layerId` on actions adds them without breaking serialization).
- **Selection / move / transform** (stable action IDs are the groundwork).
- **Image / SVG file decode/encode** (boundary stays `ImageBitmap` + model).
- **Real-time collaboration** — all editing is offline, single-user; concurrent gestures are explicitly serialized (§5.4); per-source concurrency is the collaboration-era extension.
- **In-canvas rich-text editing** — text is render-and-programmatic-add, not an interactive editor.

## Proposal

The central decision is to be **neither pure vector nor pure raster, but hybrid**.

In the DrawBox v1.x we used the pure vector approach to support lossless resize and undo/redo operations.
But it is impossible to support flood fill operations this way, because they are performed on the pixel-level.
The overhead of the hybrid approach is minimal, as we already track an image to display.

The list of tools to be supported:
- Brush
- Eraser Brush
- Action Eraser
- Flood fill
And it should be easy for 3P developers to add new tools.

The source of truth is an immutable `ActionHistory`: an ordered list of `Action` records.
This will support lossless undo and redo.

To ensure that the image is re-drawn identically every single time, the dimension of the canvas is fixed upon creation.
On request, the dimension of the canvas can be changed (preserving the aspect ratio), but the resulting image might differ a bit as pixel grid might differ.

Because the app window can be resized (on desktop or in browser) or rotated (mobile), the touch coordinates must be mapped to the latent coordinate space (scaled to the [0, 1] interval).

Not to re-draw the whole (current) image from the very beginning of `ActionHistory` after undo operation, we implement a caching strategy.
A second image (checkpoint) will follow the current one, but several actions behind (it will be a configurable parameter).
In case an undo is triggered, we will have to recreate only the last few actions.

Depending on a use-case, a user may want to either display or not display the ongoing drawing action.
To support the ongoing drawing action, we will draw it on a separate canvas of the same size (active image), and merge the active and current images together.

After an ongoing drawing action is finished, it can be optimized (simplifying path or applying effects) before being stored in the `ActionHistory`.

Actions that meant to be done in a pixel space (e.g. color fill) have access to the current image in order to be performed.
Other actions (e.g. Action Eraser) will have access to the `ActionHistory` in order to be performed.

## Alternatives considered

### Alternative 1 to the hybrid approach: stay pure vector

Pros:
- Simplicity

Cons:
- Can's support pixel-level tools (e.g. the flood fill)

### Alternative 2 to the hybrid approach: pure raster
Pros:
- Native support to all pixel manipulation tools

Cons:
- Massive memory footprint for history
- Some tools (e.g. Action Eraser) couldn't be supported
- Lossy scaling
- Difficult to serialize efficiently
